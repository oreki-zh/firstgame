# 一个月 MVP 制作计划

更新日期：2026-09-09。

本文件区分用户确认的投入与方向，以及助手建议的排期和验收标准。四周是相对制作周，实际启动日未确定；这不是后台自动执行任务或已验证的交付保证。

## 1. 已确认的制作条件

- 用户每周约 10 小时，四周约 40 小时。
- 用户负责整体关卡、系统、技能、故事线、人物特性与职业设计。
- 用户引导助手完成代码、像素绘画和文字；用户不懂编程。
- 引擎选择 Godot，目标支持 macOS 与 Windows。
- 以鼠标点击地点、人物或队伍前往行动为探索方向；用户喜欢《Griftlands》点击进入地点的感觉。
- 首段旅程未定，雪山是候选。
- 用户接受小范围 MVP，以及失败撤退并丢失部分物品。

## 2. MVP 验证目标（助手提案）

一段约 15～25 分钟、可独立开始与结束、可重新出发的旅程，验证：

1. 同行成员或分工变化，能改变信息、解决方法或经历。
2. 准备和路线存在能被玩家理解的取舍。
3. 一名旅人的经历在旅程后产生可感知的成长。

四类准备条是需在第一周验证的技术与玩法风险；它们不能占满整个制作月而挤掉完整旅程。

## 3. 范围上限

这是用户第三轮接受的小范围提案的记录。数量是上限，允许根据试玩减少，不是要求做满。

| 内容 | 上限与约束 |
| --- | --- |
| 地区 | 一个国家的一小块地区 |
| 城市 | 一个出发点，打听、赚钱、采购三类准备行为 |
| 旅人 | 四名预设旅人，选三名出发；各一个明显特性与少量技能 |
| 路线 | 一张手工地图、两条有不同取舍的路线 |
| 事件 | 约四个，部分受情报、道具或成员影响 |
| 露营 | 一个营地，三至四种分工活动，一种天气条件 |
| 战斗 | 一种敌人组合，验证四类准备条、预备指令、暂停 |
| 卡牌 | 四至六张固定卡，暂不做完整收集与组牌 |
| 成长 | 一条短个人事件链，完成一次特性变化 |
| 失败 | 撤退并丢失部分物品，损失细节待定 |
| 结尾 | 抵达与旅程结算，可以重新开始 |

完整捏人、全职业树、随机旅人、多国、多卷章继承、大量换装和完整元素体系留在长期设计中，不作为本月前置条件。

## 4. 每周 10 小时的用户安排（助手提案）

下表仅分配用户的设计和试玩时间；代码、素材迭代和构建另需助手实际工作，不应把 40 小时说成整个项目总成本。

| 周 | 用户时间分配 | 用户提供或决定 | 对应实现与验收目标 |
| --- | --- | --- | --- |
| 第 1 周 | 2 小时定首段旅程；3 小时路线与选择；2 小时旅人和技能；3 小时试玩与复盘 | 一句话目标、两条路线取舍、三至四名旅人的简要设计、首批技能 | Godot 项目可运行；占位地图可点击到达；最小准备条遭遇可操作；尝试两平台导出 |
| 第 2 周 | 3 小时城市及途中事件；2 小时露营；2 小时失败及成长规则；3 小时试玩 | 少量事件规则、营地分工、物品损失候选、成长触发 | 从城市准备到旅行结束或撤退完整跑通；无需临时修改代码才能继续 |
| 第 3 周 | 2 小时技能平衡；2 小时路线与角色内容修订；2 小时美术文字审阅；4 小时外部试玩与复盘 | 根据实际玩法选择修改内容，审阅首批正式素材 | 换队伍或准备能改变体验；完成一次成长；寻找 Windows 测试者并验证运行 |
| 第 4 周 | 2 小时确定必须修的问题；2 小时终审文字与素材；4 小时双平台验收协调；2 小时机动 | 按严重程度收敛反馈，停止新增系统 | macOS 与 Windows 测试包可启动、可玩到结尾、可重开；记录尚存问题 |

### 检查点

- 第 1 周：建立修改—运行—试玩—修复的工作循环。第一周末根据实际速度调整数量。
- 第 2 周：必须能完整玩一遍；若未接通，先减卡牌、技能和事件数量。
- 第 3 周：第三方能看出准备、成员和路线的差异。Windows 测试不能全部推到最后一天。
- 第 4 周：冻结新增系统，以修复、节奏和可运行版本为主。

如遭遇规则复杂度超过预期，先删额外武器流派、技能变体和内容数量；暂停、预备动作及行动优先级仍需保持一致。任何进一步缩减核心方向的决定要向用户说明。

## 5. 用户可以直接提供的设计格式

### 地点／事件

- 名称与场景感觉。
- 玩家提前知道什么。
- 玩家要作出的选择。
- 哪名旅人、哪种特性或物品能改变选项。
- 每个选项的收益、代价及后续影响。
- 玩家如何得知结果。

### 技能

- 名称与希望产生的体验。
- 哪名旅人或职业使用。
- 使用场景：战斗、生活，或两者。
- 目标、效果、消耗、持续时间与触发条件；没想好的数值可以留空。
- 与其他技能或物品的配合。

### 旅人

- 身份、性格和愿望。
- 擅长与不擅长什么。
- 一项最有辨识度的能力。
- 一个希望玩家遇到的个人选择。
- 这次短旅程结束后可能发生的变化。

用户无需编写代码、技术格式或引擎配置。助手将自然语言设计转成结构化数据和代码，并将需要用户决策的分歧单独标出。

## 6. 美术与文字安排（助手提案）

- 第一周做一小套风格样本：一个旅人、一段环境、一个营地物件和一个代表性风景；用户给方向并审阅。
- 样本用于判断比例、配色、可辨识性与制作耗时，不在玩法未定时扩展完整素材库。
- 核心流程先用占位素材跑通，第三周再集中替换玩家反复看到的内容。
- 文字先围绕已能运行的事件写短稿，由用户审阅故事意图，避免大量世界观文本先于玩法。
- 雪山未定案前，不批量制作雪山专属素材。

## 7. Godot 工作方式与 skill（助手提案）

先建立轻量项目开发约定，再从实际跑通的流程提炼专用 skill。优先内容是：

- 项目结构与场景职责。
- 旅人、技能、事件、物品数据如何存放与修改。
- 素材如何导入与检查。
- 如何运行、捕获错误、验证关键状态和导出。
- 将用户决定与临时实现参数区分记录。

无需用户先学习编程，也不以开发专用连接器或写完整引擎手册为前置工作。本轮只记录提案，尚未创建 skill 或开发约定文件。

当前协作机器是 Mac，建议先在本机开发和试玩，准备 macOS 与 Windows 导出配置。Godot 支持相应导出工作流；导出成功与目标系统运行测试应分开记录。Windows 测试设备或测试者尚未确定，不能将其标成已验证。

来源：[Godot Windows 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)、[Godot macOS 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_macos.html)、[Godot 命令行](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)。

## 8. 当前最少需要补齐的内容

1. 首段旅程的一句话目标：为什么出发、要抵达什么或完成什么。
2. 两条路线最主要的取舍。
3. 三名起步旅人的特性与愿望；第四名可在核心流程跑通后补。

数值、队列边界和掉落细节可围绕实际遇到的案例逐项讨论。无需先回答完整世界观、全职业或所有卷章问题。
